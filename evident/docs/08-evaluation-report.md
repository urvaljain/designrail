# 8. Evaluation and adversarial testing

What was tested, how, what passed, and what was not tested. Measured figures are in [`eval-results.md`](eval-results.md), which is generated by `npm run eval` and never edited by hand. Figures quoted below are from the run on 10 November 2026.

## What was run

| Suite | Command | Result | What it exercises |
| --- | --- | --- | --- |
| Unit | `npm run test:unit` | 28 of 28 passed | Pure domain logic: taxonomy, resume parsing, sanitising, requirement extraction, pay, dedupe, freshness, matching |
| Integration | `npm run test:integration` | 39 of 39 passed | Agents, services, auth, queue and search against a real PostgreSQL 16 database |
| End to end | `npm run test:e2e` | 13 of 13 passed | The full journey in headless Chromium against a production build, with axe scans on 16 page states |
| Evaluation | `npm run eval` | Completed; see results file | Labelled component checks and 30 scripted journeys |
| Static | `npm run typecheck`, `npm run lint`, `npm run build` | Clean; 0 lint errors, 3 warnings; 22 routes built | |
| Live connectors | Manual script, not in the repository's suites | See "Live source check" | Real Greenhouse, Lever and Ashby APIs |

All of this ran in one sandbox on one machine. The GitHub Actions workflow that would repeat it in CI has not been run.

## Adversarial scenarios

| Scenario | How the system responds | Where it is tested |
| --- | --- | --- |
| **Duplicate listings** | Reposts are keyed on normalised employer, title and location and compared by content; the later or less authoritative copy is linked to the original and hidden from search; the job page says "This is a repost" | Unit `clusters near-identical reposts`; integration `normalises listings, links reposts`, `links reposts across sources that spell the employer differently`; e2e `hides reposts`; eval 10 of 10 pairs |
| **Expired listings** | A listing absent from its source's next sync is closed and leaves search; a dead apply link (404 or 410) closes it; ambiguous link failures do not; saved applications show "Listing closed" and get a reminder to archive | Integration `closes listings the source stops listing`, `closes a listing only on a definite dead link` |
| **Source returns nothing or garbage** | A collapse to under 30% of open listings closes nothing and marks the run degraded; malformed entries are skipped and counted; unusable links drop the listing; a 5xx fails the run and leaves data untouched | Integration `does not mass-close…`, `skips malformed entries…`, `records a failed run when the source is down` |
| **Incorrect salary estimates** | There are none: pay is shown only when stated. Implausible stated figures are withheld and flagged | Unit `withholds implausible figures`, `never invents pay`; e2e `Pay withheld`; eval 14 of 14, 0 wrongly shown |
| **Missing or fabricated recruiter details** | The product holds no recruiter data. Drafts use only a recipient the user types; otherwise a neutral greeting and a listed unknown. Model edits that add an email, phone number, link or figure are rejected | Integration `never invents a recipient`; e2e outreach test; eval 4 of 4 fabricated drafts blocked |
| **Resume parsing failures** | Empty and garbled text fail with a specific message; a failed parse never replaces the active resume; thin resumes are marked for review and lower match confidence; unreadable files return an error instead of throwing | Unit `fails closed on empty and garbled input`, `flags a skills-only resume`; integration `keeps the previous resume active…` |
| **Hallucinated experience and skills** | Model-proposed skills need a verbatim resume quote; cover notes may not add numbers, skills or seniority; interview feedback must quote the answer, and scores stay within 20 points of the rubric | Integration (4 tests in `model failures and hallucinations`); eval 21 of 21 fabrications blocked, 12 of 12 faithful outputs kept |
| **Conflicting job requirements** | Entry-level with 5+ years, remote with on-site, and inconsistent year counts are each flagged on the listing, lower match confidence, and demote the listing | Unit `detects conflicting requirements`; integration; e2e integrity test |
| **LLM API outages** | Every model call has a deterministic fallback; the run is marked degraded with the reason; after 3 transient failures a breaker stops calls for 60 seconds; timeouts behave the same | Integration `degrades to the deterministic engine…`, `opens a circuit breaker…`; eval: 10 of 10 journeys complete with the provider down |
| **Prompt injection through job descriptions** | Hidden HTML and comments are dropped and flagged; AI-directed sentences are flagged and removed before extraction; listing text is never sent to a model; flagged listings are demoted and labelled | Unit (5 tests); integration `flags injected and contradictory listings…`, `never sends injected job text to a model…`; e2e; eval 14 of 14 detected |
| **Prompt injection through resumes and answers** | Text is delimited as untrusted with a system instruction to ignore embedded instructions; outputs are still verified; the rubric ignores instructions in an answer | Integration `bounds model interview scores…` |
| **Unauthorised data access** | Every user-data query is scoped by the session's user id; foreign ids return "not found"; unauthenticated export returns 401 | Integration: 10 cross-user operations rejected, exports and analytics scoped; e2e: second user gets 404 |
| **Hostile input** | Search and filters are parameterised; hostile strings return results or nothing, never an error | Integration `treats hostile search input as text` |
| **Concurrent users and background tasks** | 8 users running the journey at once all succeed; three simultaneous saves of one job yield one application; 12 workers draining 40 jobs process each exactly once; reminder planning run concurrently creates no duplicates; a crashed worker's job is reclaimed | Integration `handles many users working at once…`, `delivers each job to exactly one of many concurrent workers`, `creates each reminder once…`, `reclaims a job whose worker died…` |

## Defects the evaluation found, and what changed

The harness and the live check were useful because they failed first.

| Found by | Defect | Fix |
| --- | --- | --- |
| Live check (Ashby) | Pay in CAD, AUD and SGD was rejected as implausible: 10 of 75 listings | Currency handling generalised; unknown ISO codes get structural checks only |
| Live check (Greenhouse) | Pay stated on the line after a "Salary Range" heading was missed: 0 of 253 read | A pay heading now carries context to the next two lines; 113 read afterwards |
| Live check (Greenhouse) | Headings with typographic apostrophes ("What you’ll bring") were not recognised: 124 of 253 listings structured | Apostrophes normalised and heading patterns widened; 254 of 254 afterwards |
| Eval | Two benign sentences flagged as injection ("You are now ready to…", "As an assistant manager…") | Patterns narrowed |
| Eval | "js" matched inside "Node.js"; "sales data" and "operations team" read as skills; a fictional employer's name matched "logistics" | Alias boundary fixed; generic aliases removed |
| Eval | "Familiarity with Docker" inside a Requirements section was scored as optional | The cue no longer downgrades must-haves |
| Integration | A faithful cover note was rejected because the employer's name contained digits | Employer name added to the allowed-figures set |
| e2e harness | A database reset was refused by Prisma's safeguard against AI-run destructive commands | Left in place. Tests were redesigned to need no reset |

**In-sample caveat.** The injection, skill and requirement figures above were measured after fixing defects that the same data exposed, so they overstate performance on unseen text. The genuinely out-of-sample evidence is the live source check.

## What was not tested

- **A live model.** Prompt quality, real output distributions, refusals, latency and cost are untested. The verification layer was tested against scripted outputs written to be wrong in specific ways; a real model may be wrong in ways not anticipated.
- **Real users and real resumes.** Three synthetic resumes, all cleanly formatted. PDF and DOCX extraction is implemented and was not tested on real files; multi-column layouts and scanned PDFs are known hard cases.
- **Matching validity.** No evidence yet that a higher fit score predicts a better outcome.
- **Docker image, CI workflow, OAuth with live providers, any deployed environment.**
- **Load.** Concurrency was tested at 8 users and 12 workers on one machine, not under sustained load.
- **Accessibility with assistive technology.** Automated scans only.
- **Security review or penetration test** by anyone other than the author.
- **Non-English text, right-to-left scripts, very long documents.**

## Known limitations of the approach

1. **Lexical matching has a recall ceiling.** A skill described without its usual name is missed unless a model proposes it. One labelled skill in three resumes was missed this way.
2. **A quote check is not an entailment check.** It proves a line exists, not that the line supports the claim.
3. **Requirement extraction depends on listing structure.** Unstructured listings get lower confidence, and requirements stated only in prose may be missed.
4. **The demo board is tidy.** Real listings are messier; the live check covered three employers' boards.
5. **Rubric scores reward form.** A well-structured, specific, wrong answer to a behavioural question scores well. Concept questions check expected points by keyword, which a fluent answer can hit without understanding.
